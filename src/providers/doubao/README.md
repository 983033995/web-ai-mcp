# Experimental Doubao HTTP Provider

Current source only. On 2026-10-14, own-account Node.js HTTP requests returned complete replies and a same-conversation follow-up recalled the first-turn marker. An earlier probe encountered CAPTCHA code 710022004 before SSE_ACK. Later both current and original captured configurations succeeded, so expired credentials or a stale signature are not established causes. The website's internal risk rule remains unknown; this does not establish stable or unrestricted HTTP access. See [the investigation record](../../../docs/DOUBAO_RISK_INVESTIGATION.md). Browser fetch success is not evidence of Node.js HTTP compatibility.

Separate [expert, reasoning and file tests](../../../docs/DOUBAO_CAPABILITY_VALIDATION.md) confirmed website/HTTP protocol capabilities, including a Node-owned TXT upload and correct attachment readback. The product now implements expert parameters, thinking-container parsing and bounded TXT upload. Diagnostic response inspection remains distinct from actual MCP stdio feature validation.

Configure `DOUBAO_COOKIE`, `DOUBAO_CHAT_URL` and `DOUBAO_USER_AGENT` from the same own-account `POST /chat/completion` request in the website Network panel. Cookie must include sessionid, passport_csrf_token (or passport_csrf_token_default) and s_v_web_id. The complete URL must include aid=497858, device_id, web_id, tea_uuid, fp, pc_version, region, sys_region and web_tab_id; fp must match s_v_web_id. Never share signed URLs or credentials. `DOUBAO_TIMEOUT` defaults to 60000ms. Only the exact website origin/path or HTTP loopback fixture is accepted; redirects are rejected.

Tools: `doubao_chat`, `doubao_reasoner`, `doubao_analyze_files`, `doubao_sessions_list`, `doubao_session_close`. `mode=expert` or `thinking=true` selects the observed expert model; `show_reasoning` reveals website-visible thinking, separated from the final answer by parent-block lineage. File analysis creates a new conversation and accepts nonempty TXT files from WEB_AI_ALLOWED_ROOTS (5 files, 10 MiB each, 20 MiB total); its returned key supports follow-up. System prompt is a plain text prefix, not a system role. Search remains disabled. Resumption requires complete conversation/section/assistant-message/index/local-conversation metadata and advancing reply indices; missing metadata yields an answer without a resumable key. CHUNK_DELTA inherits the last single content-block patch, including across TTS events. File metadata and loading-block deletion patches are handled. Truncated, unknown or malformed SSE fails closed. Requests are not retried automatically.

Image/video generation was requested and verified on 2026-10-19. Three additional tools are available (nine tools total for a Doubao-only server, including `webai_providers`):

- `doubao_generate_image`: required `prompt`, optional `ratio=auto|1:1`; observed Seedream 5.0 Flash website ability.
- `doubao_generate_video`: required `prompt`, optional `ratio=auto|1:1|3:4|4:3|9:16|16:9|21:9`, integer `duration_seconds=4..30` (default 4); observed Seedance 2.5 website ability.
- `doubao_media_status`: required local `session_key`; one read of `/im/chain/single`, restricted to the latest 20 messages in that conversation. It never creates/retries a generation. Later assistant reply lineage is committed atomically so a delivered video can be followed up after restart.

Generation creates a separate conversation by default, without using or replacing the project default. `session_key` or `conversation_name` can select a continuation. The website may ask for confirmation; reply using `doubao_chat` with the same key, then query results. `media_status=no_media_returned` means no creation card has been returned; it does not establish that a job is queued. The server never infers completion from prose, automatically confirms, polls, or resubmits. Actual creation cards expose `media` entries with type, status, result URL, dimensions and optional video duration. Unknown website statuses are `unavailable`, never completed. Only observed HTTPS media hosts are accepted, and no media URLs or prompts are persisted in the session store. Result URLs may expire; automatic download, image references/editing and image-to-video are not implemented. Model availability, exact output specifications, quota and billing remain controlled by the website.

Use `DOUBAO_TIMEOUT=120000` and a longer MCP client timeout for generation. Actual MCP image creation, a four-second video and result lookup after restart passed; both result URLs returned HTTP 206 with the corresponding image/video content type. See [media validation](../../../docs/DOUBAO_MEDIA_VALIDATION.md) for evidence and limits. npm v0.1.2 does not contain this source-only integration.

Run `npm run smoke:local` for local HTTP/stdio fixtures. To opt into two own-account website test messages, run `npx tsx scripts/probe-doubao.ts --env-file /private/path/.env --live`. Add `--features` after building for four actual MCP stdio messages covering expert thinking, TXT upload and file follow-up after restart (not generation). It returns nonzero on configuration, transport or validation failure without printing replies or IDs.

Website request context may change. No CAPTCHA/WAF/rate-limit bypass, account rotation, chat-signature generation or browser fallback is implemented. Upload authentication uses the website's own temporary storage credentials; storage requests do not receive the website Cookie. CAPTCHA stops all further chat writes from that client until it is recreated. An HTTP challenge does not automatically appear in an existing website tab, and successful website chat alone does not prove HTTP recovery. Use the official verification interface when a challenge is presented, refresh the complete configuration from one own-account request and restart MCP; confirm recovery with an explicit HTTP probe. Do not keep probing a blocked client or treat compilation or fixture success as live support.
